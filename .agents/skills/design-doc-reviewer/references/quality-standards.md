## 二、评审意见编写规范

### 2.1 问题描述格式

每条评审意见必须包含以下要素：

```markdown
**[问题编号]** [问题类型]：[问题概述]
- 📍 **原文定位**：「[引用策划案原文]」（位于第X章第Y节）
- 🔴/🟡/🟠/🟢 **影响等级**：[阻断/严重/一般/建议]
- 📝 **问题详述**：[详细说明为什么这是问题]
- 💡 **修改建议**：[给出具体的、可直接执行的建议]
```

### 2.2 良好 vs 不良评审意见对比

#### ❌ 不良示例

```
问题：使用流程写得不够清楚
建议：需要改进
```

问题：
- 没有引用原文
- 没有说明具体哪里不清楚
- 建议空泛不可执行

#### ✅ 良好示例

```
**[P-003]** 模糊：操作步骤缺少关键细节
- 📍 原文定位：「第二步：用户点击配置按钮进行设置」（第2.2节）
- 🟡 影响等级：严重
- 📝 问题详述：未说明"配置按钮"的具体位置（工具栏？右键菜单？属性面板？），
  也未描述点击后出现什么界面，新手用户将无法定位操作入口。
- 💡 修改建议：补充按钮位置描述，例如"在工具栏右侧点击[⚙️配置]按钮，
  弹出配置面板（位于编辑器右侧停靠区），面板包含：[列出具体控件]"
```

### 2.3 亮点认可格式

评审不能只找问题，也要指出做得好的地方：

```markdown
### ✅ 亮点认可
1. **[亮点描述]**：[具体说明好在哪里]
   - 📍 位置：[章节位置]
   - 💡 推广建议：[是否可在其他策划案中复用该模式]
```

## 三、补充建议编写规范

### 3.1 缺失内容补充建议格式

```markdown
## 🔧 补充建议 #[编号]：[建议补充的模块/内容]

### 当前状态
[描述当前缺失什么，引用模板中的要求]

### 建议补充内容
[给出详细的补充内容建议，具体到可以直接复制到策划案中使用]

### 补充优先级
🔴 必须补充 / 🟡 建议补充 / 🟢 有余力时补充

### 补充理由
[解释为什么需要这部分内容，缺失会导致什么后果]

### 参考示例
[如果有的话，给出类似功能的参考写法]
```

### 3.2 补充建议的详细程度

| 优先级 | 建议详细度 | 示例 |
|--------|-----------|------|
| 🔴 必须 | 给出可直接使用的完整内容 | 直接写出缺失的数据结构表 |
| 🟡 建议 | 给出框架+关键内容 | 列出需要包含的字段，标注类型 |
| 🟢 有余力 | 给出方向+参考 | 说明应该补充什么方向的内容 |

## 四、评分一致性规范

### 4.1 评分偏差控制

为确保评分一致性，遵循以下原则：

1. **对标评分**：评分前先回顾评分标准表（review-checklist.md 第二节）
2. **证据支撑**：每个维度的评分必须有至少1条原文引用作为支撑
3. **整体平衡**：总分应与单项分数逻辑一致（不出现单项都低但总分高的情况）
4. **相对锚定**：如有该团队的历史评审数据，参考历史评分分布

### 4.2 评分争议处理

当某个维度难以评分时：
```
评分：[X]分
⚠️ 评分说明：[解释评分理由]
📝 不确定因素：[说明为什么难以确定]
💡 建议验证：[建议通过什么方式验证]
```

## 五、评审报告质量自检

### 5.1 自检清单

评审报告完成后，逐项自检：

| 序号 | 检查项 | 通过标准 |
|------|--------|---------|
| 1 | 所有必填模块是否评审？ | 模板必填模块100%覆盖 |
| 2 | 每个问题是否有原文定位？ | 100%问题有原文引用 |
| 3 | 每个问题是否有改进建议？ | 100%问题有可执行建议 |
| 4 | 问题是否分级？ | 使用🔴🟡🟠🟢四级分类 |
| 5 | 是否有亮点认可？ | 至少包含1条正面评价 |
| 6 | 评分是否有依据？ | 每个维度评分有原文支撑 |
| 7 | 行动计划是否具体？ | 每项行动有负责人和时间建议 |
| 8 | 中文是否有乱码？ | UTF-8编码，无乱码字符 |
| 9 | 格式是否规范？ | Markdown格式正确渲染 |
| 10 | 是否避免主观臆断？ | 判断基于事实和标准 |

### 5.2 常见评审偏差

| 偏差类型 | 表现 | 纠正方法 |
|---------|------|---------|
| **过严** | 对所有细节都标注为严重问题 | 区分影响等级，只有真正阻断开发的才标🔴 |
| **过松** | 明显问题标记为建议级 | 按影响矩阵客观评估 |
| **选择性忽视** | 只评审自己擅长的维度 | 按模板逐章检查，不跳过 |
| **重复计数** | 同一问题在多处重复记录 | 同一根因只记录一次，关联位置列在一起 |
| **只批不建** | 指出问题但不给解决方案 | 每个问题必须附带改进建议 |
