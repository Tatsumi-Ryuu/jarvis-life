# 策划案评审检查清单与评分标准

本文档为评审 Skill 的核心参考，提供标准化的检查清单和评分标准。

---

## 一、基础检查清单

### 1.1 最低可评审条件

在开始评审前，确认文档满足以下条件，否则应返回"不具备评审条件"的反馈：

- [ ] 文档是否包含明确的功能目标描述？
- [ ] 文档是否有基本的结构框架？
- [ ] 文档是否包含可识别的核心功能模块？
- [ ] 文档是否超过500字（过短可能是大纲而非策划案）？

### 1.2 内容准确性检查

| 序号 | 检查项 | 检查方法 | 严重程度 |
|------|--------|---------|---------|
| 1 | 术语一致性 | 搜索同义词/近义词使用情况 | 🟡 |
| 2 | 格式规范性 | 检查标题层级、编号、表格 | 🟢 |
| 3 | 逻辑自洽性 | 检查前后描述是否矛盾 | 🔴 |
| 4 | 事实正确性 | 验证API名称、平台规则等 | 🔴 |
| 5 | 数值合理性 | 检查性能指标、数量级是否合理 | 🟡 |
| 6 | 引用准确性 | 验证文档中引用的外部资料 | 🟡 |

### 1.3 无歧义性检查

| 序号 | 检查项 | 常见问题示例 | 修正方向 |
|------|--------|------------|---------|
| 1 | 模糊数量词 | "大量"、"很多"、"若干" | 替换为具体数值 |
| 2 | 模糊时间词 | "很快"、"稍后"、"适时" | 替换为具体时间/条件 |
| 3 | 模糊程度词 | "流畅"、"美观"、"高效" | 给出量化标准 |
| 4 | 未定义缩写 | 首次使用未展开 | 首次出现时标注全称 |
| 5 | 暗含假设 | 未说明的前置条件 | 明确列出所有前提 |

### 1.4 可测试性检查

- [ ] 验收标准是否可量化、可测量？
- [ ] 边界条件是否已明确定义？
- [ ] 异常处理是否覆盖主要场景？
- [ ] 性能指标是否有具体数值？

## 二、评分标准

### 2.1 总体评分维度

| 维度 | 权重 | 评分标准 |
|-----|-----|---------|
| **战略对齐度** | 20% | 功能是否与产品战略方向一致 |
| **内容完整性** | 25% | 模板必填模块是否全部覆盖 |
| **技术可行性** | 25% | 技术方案是否可落地实现 |
| **表达清晰度** | 15% | 新人能否直接理解并执行 |
| **风险控制** | 15% | 边界情况和异常处理是否充分 |

### 2.2 各维度评分细则

#### 战略对齐度（1-10分）

| 分数段 | 标准 |
|--------|------|
| 9-10 | 完美对齐产品战略，解决核心痛点，有数据支撑 |
| 7-8 | 基本对齐，痛点清晰，但数据支撑不足 |
| 5-6 | 部分对齐，但存在方向偏差或优先级疑问 |
| 3-4 | 对齐度低，需求缘由不充分 |
| 1-2 | 与战略脱节或属于伪需求 |

#### 内容完整性（1-10分）

| 分数段 | 标准 |
|--------|------|
| 9-10 | 所有必填模块完整且详尽，选填模块按需覆盖 |
| 7-8 | 必填模块全覆盖但部分不够详细 |
| 5-6 | 缺少1-2个必填模块，或多个模块内容粗略 |
| 3-4 | 缺少3个以上必填模块 |
| 1-2 | 仅有大纲或概述，缺乏实质内容 |

#### 技术可行性（1-10分）

| 分数段 | 标准 |
|--------|------|
| 9-10 | 技术方案成熟可行，API确认可用，性能有评估 |
| 7-8 | 技术方案基本可行，少量待验证项 |
| 5-6 | 技术方案有疑问，需要原型验证 |
| 3-4 | 技术方案存在明显问题或依赖不明 |
| 1-2 | 技术方案不可行或严重缺乏技术细节 |

#### 表达清晰度（1-10分）

| 分数段 | 标准 |
|--------|------|
| 9-10 | 结构清晰、用语精准、示例充分、无歧义 |
| 7-8 | 整体清晰，少量表述需要改进 |
| 5-6 | 部分章节表述模糊，需要澄清 |
| 3-4 | 多处表述不清，理解困难 |
| 1-2 | 整体混乱，难以理解核心意图 |

#### 风险控制（1-10分）

| 分数段 | 标准 |
|--------|------|
| 9-10 | 边界情况穷举、异常处理完善、有降级方案 |
| 7-8 | 主要边界和异常已覆盖，少量遗漏 |
| 5-6 | 部分边界情况未考虑 |
| 3-4 | 大量边界情况未考虑 |
| 1-2 | 几乎没有异常处理和边界考虑 |

### 2.3 决策矩阵

| 总分范围 | 决策建议 | 说明 |
|---------|---------|------|
| 8.0-10.0 | 🟢 保留并推进 | 小幅修订后可进入开发 |
| 6.0-7.9 | 🟡 增强后推进 | 需完成关键修订后再评审 |
| 4.0-5.9 | 🟠 重大修订 | 存在多个严重问题，需大幅修改 |
| 1.0-3.9 | 🔴 暂停/砍掉 | 存在根本性问题，需重新规划 |

## 三、问题分类与影响等级

### 3.1 影响等级定义

| 等级 | 标记 | 定义 | 处理要求 |
|------|------|------|---------|
| **阻断** | 🔴 | 如不解决，开发无法开始 | 必须在下个版本前修复 |
| **严重** | 🟡 | 会导致重大功能缺陷或返工 | 强烈建议在开发前修复 |
| **一般** | 🟠 | 影响用户体验或可维护性 | 建议在开发中解决 |
| **建议** | 🟢 | 优化建议，可提升质量 | 有余力时考虑 |

### 3.2 常见问题类型

| 问题类型 | 说明 | 典型表现 |
|---------|------|---------|
| **缺失** | 应有但未包含的内容 | 缺少异常处理、缺少性能指标 |
| **模糊** | 存在但描述不清 | "用户可操作"但未说明具体步骤 |
| **矛盾** | 前后描述不一致 | 第2节说A，第4节的流程图表现为B |
| **过度** | 不必要的过度设计 | 为简单功能设计了过于复杂的架构 |
| **不足** | 关键细节不够深入 | 数据结构只列了字段名没有类型和说明 |
| **错误** | 事实性错误 | 引用了不存在的API或错误的平台规则 |

## 四、需求不明确示例参考

| 模糊描述 | 问题分析 | 澄清要求 |
|---------|---------|---------|
| "用户可领取时要播放音效和动画" | 缺少资源具体信息 | 动画layout路径？音效ID？播放时机？ |
| "用户分享操作需要上报" | 缺少技术实现细节 | 上报时机？目标系统？数据格式？ |
| "界面要流畅美观" | 缺少量化标准 | 帧率要求？响应时间？UI规范？ |
| "支持多种奖励类型" | 缺少具体范围 | 支持哪些类型？数据结构？显示方式？ |
| "系统要稳定可靠" | 缺少可测量标准 | 可用性要求？错误率容忍？降级策略？ |
| "操作要简单易用" | 缺少具体交互设计 | 几步完成？有无引导？容错机制？ |
